## Introduction  

Our group chose group 17's codebase due to some key concerns caught early in the compiling and testing process as well as some of the file architecture decisions made. The codebase already had .bun files present which were either valid or invalid, which were useful for testing that the codebase worked appropriately. Additionally, the codebase included a report.md file stating the software decisions made, tools used, and challenges faced. This allowed our group to focus on potential edge cases not covered or unresolved by the codebase, and pinpoint what kind of vulnerabilities could be expected, given that a decent portion of the project was generated by multiple AI tools with differing context windows and capabilities. This made our group suspicious of how well the functions behaved under these AI tools, as we expected them to fail to coordinate the consistency and handling required to produce a robust BUN parser.  

Our testing approach was structured around the categories listed in the Phase 2 brief: crashes, excessive memory usage, hangs, and incorrect outputs. We also focussed on the six areas of the BUN specification that the brief identifies as boundary-sensitive: zero-length sections, maximum field values, overlapping sections, RLE and uncompressed_size mismatches, asset-name bounds, and large `asset_count`. Six findings were ultimately confirmed and are reproduced automatically by the accompanying package via `make reproduce`. The findings cluster into two main types: linear or unbounded resource allocation, and mishandled validation logic.

## Assumptions and method

### General assumptions

For the purposes of this project, we make the following assumptions:

1. The parser is compiled with the default flags plus `-fsanitize=address,undefined,leak -fno-omit-frame-pointer -g -O0` for sanitizer testing. we compile without sanitizers for the calloc-shim test (F-02), because AddressSanitizer replaces `calloc` with its own version at link time, which would prevent our `LD_PRELOAD` shim from intercepting calls.
2. The parser is to be run on Ubuntu 24.04 x86-64 (CITS3007 SDE).
3. Sparse files can be used to simulate large file sizes (>1 GB), so we can avoid disk overhead.

### Testing approach and tools

For testing, our focus was to read the main files in the codebase: `bun_parse.c`, `bun.h`, and `main.c`. While closely reading each line in these files, we consistently cross-referenced it with the provided BUN specification to ensure all requirements were addressed as expected. Then our group proceeded by running test fixtures on both the standard and sanitizer-enabled binaries.

  

When testing using codebase using the provided .bun invalid and valid test files we observed no failures and the printed summary output as expected. However, it was noticed that when testing files 15-rle-bomb.bun and 16-rle-truncated.bun, the codebase was catching on offset size requirements and moving to the next asset too quickly before having the chance to detect the invalid rle logic. This behaviour was not expected eventhough it is not completely incorrect. As a result, our group started to closely compare essential requirements stated in the project brief and bun specification that group 17 may have overlooked when writing their logic for the codebase.

  

  

**Specifically the following tools and techniques were applied:**

  

- **GCC 13.3.0 with `-Wformat-truncation=2 -Wformat-overflow=2` for static warnings beyond the team's default `-Wformat-truncation=1` (caught F-03).**

- **AddressSanitizer + LeakSanitizer via `-fsanitize=address,leak` (caught F-01).**

- **UndefinedBehaviorSanitizer via `-fsanitize=undefined` for null-pointer and integer-overflow checking (no findings, but used to validate negative cases).**

- **Two `LD_PRELOAD` shims authored for this audit:**

    - **`fault_shim.c` — fails the Nth `fseeko()` call to inject I/O failure into the asset-iteration loop (drives F-01).**

    - **`zero_calloc_shim.c` — makes `calloc(0, *)` return NULL, exercising the implementation-defined behaviour permitted by C11 §7.22.3¶1 (drives F-02).**

- **Crafted boundary-value `.bun` files generated by `scripts/gen_probes.py` covering: empty sections, asset records at table boundaries, large `asset_count` (25M, sparse file), and intentional spec-violating inputs.**

  

**Tools we considered but did not need: `valgrind` (LeakSanitizer covered the leak detection), `cppcheck` and `clang --analyze` (group 17's project already passes `-Wall -Wextra -Wconversion` cleanly; running these additional static analysers would be due diligence but did not surface anything our targeted tests missed). All findings below are reproducible through normal parser execution — the shims simulate environmental conditions rather than modify the parser itself.**

  

**Negative results — what we tested and did not find:**

  

- **All 22 supplied fixtures (6 valid, 16 invalid) ran cleanly under ASan/UBSan/LSan; exit codes matched spec expectations.**

- **A 340-input fuzz harness (random-valid, header-mangled, truncated, asset-record-mangled, and wholly-random inputs) produced zero sanitizer hits.**

- **Boundary cases including a name spanning the entire string table, a 60-byte header-only file, and an asset whose data ends exactly at the data-section boundary all parsed correctly.**





`LD_PRELOAD` shims are used in two findings (F-01, F-02) to deterministically drive code paths that would otherwise require an adversarial filesystem (e.g., a file truncated between two `fseeko` calls) or a non-glibc libc. Shim sources are short (15-25 lines each) and shipped with the reproduction package.

  

## Findings

  

### Finding F-01 

- **ID:** F-01
- **Category:** Excessive memory use
- **Spec reference:** Brief §5.3 which says the parser must not crash or produce incorrect output on well-formed files.
- **Assumptions:** We can use a small fault-injection `LD_PRELOAD` shim, `fault_shim.c`, which has been provided in the reproduction package. Without the shim, the same leak occurs whenever a multi-asset file is truncated between asset records. However, triggering it deterministically with a static fixture is brittle, so the shim provides an easy reproduction of the finding. 

**Description**
`bun_parse_assets` allocates `str_buf` via `realloc` for each asset name while iterating over asset records. When any `fseeko` or `fread` fails mid-loop, the function takes an early `return BUN_ERR_IO` without freeing `str_buf`. There are four such early-return sites in the loop (lines 322, 433, 444, 471). The realloc on line `474` also has `p = realloc(p, n)` which means on failure the original block is leaked because `p` has been overwritten to NULL.  

**Expected behaviour**
For any input the parser should exit without leaking heap memory. LeakSanitizer should report zero direct leaks.

**Actual behaviour**
LeakSanitizer reports a direct leak rooted at `bun_parse.c:474`, with the allocation traced back to the asset-loop realloc.

**Reproduction steps**

  1. Build the parser with sanitizers from the package root, with target source code in `target/`):

   ```
   cd target && make CFLAGS="-std=c11 -pedantic-errors -Wall -Wextra \

       -Wconversion -Werror=vla -Werror=implicit-function-declaration \

       -fsanitize=address,undefined,leak -fno-omit-frame-pointer -g -O0"

   mv target/bun_parser bun_parser_san
   ```

2. Build the fault-injection shim from `fault_shim.c`:

   ```
   gcc -shared -fPIC fault_shim.c -o fault_shim.so -ldl
   ```

3. Generate the probe inputs:

   ```
   python3 scripts/gen_probes.py tests/fixtures/crafted
   ```

4. Run with the shim preloaded after libasan, failingthe 4th `fseeko` call which is the seek to asset 1's string-table entry:

   ```
   ASAN_LIB=$(ldd ./bun_parser_san | awk '/libasan/{print $3}')
   LD_PRELOAD="$ASAN_LIB:$(pwd)/fault_shim.so" FAULT_NTH=4 \
   ASAN_OPTIONS=detect_leaks=1:exitcode=23 \
       ./bun_parser_san tests/fixtures/crafted/probe_two_assets.bun
   ```

5. Observe the LeakSanitizer report on stderr:
   ```
   [shim] failing fseeko call #4
   
   === Errors ===
   Error 1: (3) Failed to seek to string table name of asset record 1 

   ==…==ERROR: LeakSanitizer: detected memory leaks

   Direct leak of 5 byte(s) in 1 object(s) allocated from:
       #0 …  in realloc …
       #1 …  in bun_parse_assets bun_parse.c:474
       #2 …  in main main.c:226

   SUMMARY: AddressSanitizer: 5 byte(s) leaked in 1 allocation(s).
   ```

   Exit code is 23 which comes from from `ASAN_OPTIONS=exitcode=23`.

Alternatively, run `make reproduce_f01` in the reproduction package to execute this test automaticaly.

### Finding F-02
- **ID:** F-02
- **Category:** Incorrect output
- **Spec reference:** bun-spec §4 `u32 asset_count` has no minimum stated assets so zero is permitted by the type. §5.2.c says we need to"Exit with status code 0 (BUN_OK)" for valid files.
- **Assumptions:** We use a 15-line `LD_PRELOAD` shim in `zero_calloc_shim.c`, provided to make `calloc(0, *)` return NUL. This is permitted behaviour.The shim simulates the parser being run on a non-glibc system without needing to actually build for one.

**Description**
`bun_parse_assets` calls `calloc(asset_count, sizeof(int))` and `calloc(asset_count, sizeof(BunAssetRecord))` at lines 301-302, then bails with `BUN_ERR_ALLOC`. If either returns NULL. When `asset_count == 0`, both size arguments are zero, and the C11 standard explicitly permits calloc to return NULL in that case. The current code treats that NULL as an allocation failure, rejecting the file.  

**Expected behaviour**
A header with `asset_count = 0` and all other fields valid is a well-formed BUN file per spec §4 / §9.4. The parser should:
1. Return exit code 0 (BUN_OK), per brief §5.2.c.
2. Print the header on stdout, per brief §5.2.a.
3. Emit no error messages to stderr. 

**Actual behaviour**
On any libc where `calloc(0, *)` returns NULL  the parser emits `Error 1: (5) Failed to allocate memory for asset printability array` on stderr and exits with status 5. A valid file then can be wrongly rejected.

**Reproduction steps**
1. Build the parser without sanitizers from the reproduction package root:

   ```
   cd target && make CFLAGS="-std=c11 -pedantic-errors -Wall -Wextra \
       -Wconversion -Werror=vla -Werror=implicit-function-declaration -O0"
   mv target/bun_parser bun_parser_plain
   ```
   
   The plain binary is used here because ASan's allocator shadows the calloc shim, preventing the flaw from triggering.

2. Build the calloc-zero shim:

   ```
   gcc -shared -fPIC zero_calloc_shim.c -o zero_calloc_shim.so -ldl
   ```

3. Generate the probe inputs:

   ```
   python3 scripts/gen_probes.py tests/fixtures/crafted
   ```  

4. Confirm the file is accepted without the shim:

   ```
   ./bun_parser_plain tests/fixtures/crafted/probe_empty.bun ; echo "rc=$?"
   ```

   This exits with `rc=0`, and prints the header. Tjhis is expected.

5. Re-run with the shim, simulating a libc where `calloc(0, *)` returns NULL:

   ```
   LD_PRELOAD="$(pwd)/zero_calloc_shim.so" \
       ./bun_parser_plain tests/fixtures/crafted/probe_empty.bun
   echo "rc=$?"
   ```

   On stderr this then gives

   ```
   [calloc_shim] returning NULL for calloc(0,4)
   [calloc_shim] returning NULL for calloc(0,48)
  
   === Errors ===
   Error 1: (5) Failed to allocate memory for asset printability array
   ```
   Which has exit code: `rc=5`.

Alternatively, run `make reproduce_f02` in the reproduction package to execute this test automatically.

### Finding F-03
- **ID:** F-03
- **Category:** Incorrect output
- **Spec reference:** Brief §5.2.d requires "a human-readable list of spec violations found in the file – one violation per line, with enough detail for a developer to locate and fix the problem". The truncated diagnostic losesthe parser-supported compression types list, removing the actionable guidance the brief requires.
- **Assumptions:** None. Reproduces under default build flags on a ~480 KB
  crafted file.
- 
**Description**
The error message at `bun_parse.c:360` is written into a 128-byte stack buffer with `snprintf`. The fixed text is 113 bytes; the two `%u` substitutions are an asset record index, which is bounded by `asset_count` with max 10 digits as u32, and a compression value read directly from the file which is also u32. When the substitutions total ≥15 digits the message exceeds 128 bytes and `snprintf` silently truncates the tail. 

GCC `-Wformat-truncation=2` flags this site and three similar sites at lines 260, 266, 272. The team's Makefile uses the default `-Wformat-truncation=1` which only warns on guaranteed truncation, not may-truncate, so the warning was missed.

**Expected behaviour**
The full error message should appear on stderr, including the trailing `". This parser supports only types 0 (uncompressed) and 1 (RLE)"`. The part that tells the developer which compression types are supported is needed. 

**Actual behaviour**
The message is silently truncated. With `asset_count = 10,001` and the last record's `compression` field set to `UINT32_MAX (4294967295)`, the stderr output ends mid-word:

```
Error 1: (2) Asset record 10000 has unsupported compression type 4294967295. This parser supports only types 0 (uncompressed) and 1 (RLE
```

  The closing `)` is dropped. 113 fixed + 5 index digits + 10 compression digits = 128 chars + null terminator = 129 bytes into a 128-byte buffer.  

**Reproduction steps** 
1. Build the parser without sanitizers:

   ```

       -Wconversion -Werror=vla -Werror=implicit-function-declaration -O0"
   mv target/bun_parser bun_parser_plain
   ```
2. Generate the probe inputs (if not already done):

   ```
   python3 scripts/gen_probes.py tests/fixtures/crafted
   ```

3. Run the parser and observe the truncated error:

   ```
   ./bun_parser_plain tests/fixtures/crafted/probe_trunc.bun 2>&1 | grep 'compression type'
   ```

4. Observe the truncated message — ends with `1 (RLE`, missing the `)`:

   ```
   Error 1: (2) Asset record 10000 has unsupported compression type 4294967295. This parser supports only types 0 (uncompressed) and 1 (RLE
   ```

Alternatively, run `make reproduce_f03` in the reproduction package to execute this test

### Finding F-04
- **ID:** F-04
- **Category:** Excessive memory use
- **Spec reference:** Phase 2 Project Brief §5.3 which requires a sub-linear memory requirement and defines "Excessive memory use" as >1 GB during execution.
- **Assumptions:** The filesystem supports sparse files. The on-disk size of the probe is ~4 KB despite a 1.2 GB virtual size. 
  `/usr/bin/time -v` is expected to be available but the reproduction package ships a Python fallback (`scripts/measure_rss.py`) if not.

**Description**
`bun_parse_assets` allocates two arrays sized linearly in `asset_count`:
- `bun_parse.c:301`: `calloc(asset_count, sizeof(int))` giving 4 bytes per record
- `bun_parse.c:302`: `calloc(asset_count, sizeof(BunAssetRecord))` giving 48 bytes per record

The loop body at `bun_parse.c:337` then unconditionally writes `ctx->assets[i] = record` for every asset record read from disk, faulting the calloc-ed pages into physical RAM. The total memory use is therefore linear in `asset_count`, violating the sub-linear requirement. The brief recommends an iterate-and-seek pattern to read one record at a time, validate, emit any errors, and move on without retaining the full asset table in memory.

**Expected behaviour**
Peak resident set size should remain well under 1 GB regardless of `asset_count`, since the parser only needs one record in memory at a time to validate it. A sub-linear implementation would have RSS bounded by a small constant plus the file's I/O buffer.

**Actual behaviour**
With `asset_count = 25,000,000` which is a 1.2 GB sparse file, the parser's peak RSS measures **~1.15 GB** over the 1 GB threshold defined in the brief. RSS grows linearly with `asset_count`, confirmed by varying the input.

**Reproduction steps**
1. Build the parser without sanitizers:

   ```
   cd target && make CFLAGS="-std=c11 -pedantic-errors -Wall -Wextra \
       -Wconversion -Werror=vla -Werror=implicit-function-declaration -O0"
   mv target/bun_parser bun_parser_plain
   ```

2. Generate the probe inputs (if not already done):

   ```
   python3 scripts/gen_probes.py tests/fixtures/crafted
   ```

3. Run the parser under `/usr/bin/time -v` and measure peak RSS:

   ```
   /usr/bin/time -v ./bun_parser_plain \
       tests/fixtures/crafted/probe_large_assets.bun \
       2>&1 >/dev/null | grep "Maximum resident set size"
   ```  

4. Observe peak RSS exceeds the 1 GB threshold:

   ```
   Maximum resident set size (kbytes): 1173488
   ```

  ~1.15 GB, well over the brief's 1 GB definition of excessive memory use.

Alternatively, run `make reproduce_f04` in the reproduction package to execute this test automatically.

### Finding F-05
- **ID:** F-05
- **Category:** Incorrect output
- **Spec reference:** bun-spec §5.1 note 4 "If a parser detects that compression is used, and that the actual uncompressed size is different to the value of `uncompressed_size`, it must abort parsing and return `BUN_MALFORMED`." Also brief §5.2.d says errors must be reported, but the
  spec is clear that parsing must stop on this condition.
- **Assumptions:** None.

**Description**
At `bun_parse.c:458-463` the parser correctly detects an RLE uncompressed-size mismatch and calls `add_error(ctx, BUN_MALFORMED, …)`. However, it does not `return` and execution continues to the rest of the aset's processing which are lines 466-503 and to the next iteration of the asset loop. Subsequent assets are still parsed, validated, and printed to stdout. The spec language is says we "must abort parsing." Setting `ctx->result = BUN_MALFORMED` and continuing is not equivalent to aborting.  

**Expected behaviour**
On detecting the mismatch, the parser should return immediately with `BUN_MALFORMED`. No subsequent asset should be processed or printed, regardless of whether the subsequent asset itself is valid.

**Actual behaviour**
The parser records the error, returns exit code 1, but processes and prints asset 1's name, metadata, and payload to stdou before exiting. A consumer of the parser's stdout cannot distinguish the file from being fully valid compared to the file being malformed but printing some contents anyway. 

**Reproduction steps**
1. Build the parser without sanitizers:

   ```
   cd target && make CFLAGS="-std=c11 -pedantic-errors -Wall -Wextra \
       -Wconversion -Werror=vla -Werror=implicit-function-declaration -O0"
   mv target/bun_parser bun_parser_plain
   ```  

2. Generate the probe inputs:

   ```
   python3 scripts/gen_probes.py tests/fixtures/crafted
   ```

3. Run the parser:

   ```
   ./bun_parser_plain tests/fixtures/crafted/probe_rle_mismatch.bun
   echo "rc=$?"
   ```  

4. Observe that stderr correctly reports the error:

   ```
   === Errors ===
   Error 1: (1) Asset record 0 claims to have uncompressed size 10 but actually has 3
   ```

   but stdout still contains asset 1's contents:

   ```
   Asset 1:
     Asset Name: good
     ...
     Payload: ABCD
   ```

   Exit code is 1 (BUN_MALFORMED, correct), but per spec §5.1 note 4 the parser should have aborted before reaching asset 1.

Alternatively, run `make reproduce_f05` in the reproduction package to execute this test automatically.

### Finding F-06
- **ID:** F-06
- **Category:** Incorrect output
- **Spec reference:** bun-spec §9.3 says no sections can overlap. An empty section with size 0 occupies no bytes and cannot overlap anything. Rejecting such a file violates §9.3 as a false positive.
- **Assumptions:** None. 

**Description**
The parser has two overlap checks that fail to account for empty sections:
- `bun_parse.c:227-235`: tests  `section_offset < BUN_HEADER_SIZE`, ignoring section size. Any section with offset < 60 is flagged, even if its size is 0.
- `bun_parse.c:277-289`: uses the formula `A.start < B.end && A.end > B.start`. When A is empty (`A.start == A.end`). This formula incorrectly returns true whenever A.start lies strictly inside B.

Both checks reject spec-conformant files where one section is empty and positioned where another section's bytes happen to live.  

**Expected behaviour**
A header where `asset_count = 0`, regardless of its offset, should not be flagged as overlapping. The parser should accept the file and exit with status 0 BUN_OK per spec §9.3 only non-empty section overlaps violate the rule.  

**Actual behaviour**
The parser emits `(1) Asset table overlaps with string table` on stderr and exits with status 1 BUN_MALFORMED, rejecting a valid file.

**Reproduction steps**
1. Build the parser without sanitizers:

   ```
   cd target && make CFLAGS="-std=c11 -pedantic-errors -Wall -Wextra \
       -Wconversion -Werror=vla -Werror=implicit-function-declaration -O0"
   mv target/bun_parser bun_parser_plain
   ```

2. Generate the probe input

   ```
   python3 scripts/gen_probes.py tests/fixtures/crafted
   ```

   The probe `probe_empty_overlap.bun` is a 76-byte file `asset_count = 0` placed at offset 64,  strictly inside the string table at `[60, 76)`.

3. Run the parser:

   ```
   ./bun_parser_plain tests/fixtures/crafted/probe_empty_overlap.bun
   echo "rc=$?"
   ``` 

4. Observe the false-positive overlap report:
   ```
   === Errors ===
   Error 1: (1) Asset table overlaps with string table
   ```
   
   rc=1. The file is spec-conformant as the "asset table" has size 0 and cannot overlap with anything.

Alternatively, run `make reproduce_f06` in the reproduction package to execute this test automatically.

## Conclusion

Six confirmed flaws were identified, fitting into two significant categories:
- **Resource-use violations (F-01, F-04):** The parser leaks `str_buf` on mid-loop early-return paths in `bun_parse_assets` (F-01), and allocates two arrays linear in `asset_count` then touches every byte by writing each parsed record into them (F-04). Both have their cause in the same function and both stem from the same overall design choice which was to buffer the full asset table in RAM rather than implement sublinear memory usage as the brief suggests.
- **Validation logic that handles non-empty inputs correctly but mishandles boundary cases (F-02, F-05, F-06).** `calloc(asset_count, ...)` rejects `asset_count = 0` on spec-conformant libcs (F-02). The RLE uncompressed-size check records `BUN_MALFORMED` but does not abort (F-05). The section-overlap formula incorrectly flags zero-size sections positioned inside non-empty sections (F-06). These are independent bugs but share the pattern of a check that is correct for the "normal" case but incorrect at zero or edge cases. 
- **A diagnostic-truncation bug (F-03)**. This is the last flaw. It doesn't fit into the other categories and it is not a security flaw, but does violate the Phase 2 brief's requirement that error messages contain enough detail to locate and fix the problem. The truncated message drops the list of supported compression types, which is the only actionable guidance in the message.

  **Recommendations to group 17:** 
- Adopt `-Wformat-truncation=2` in `CFLAGS` to surface F-03 and similar issues at compile time.
- Refactor `bun_parse_assets` to iterate-and-seek without retaining the full asset table in RAM (addresses F-04 and removes the leak surface in F-01).
- Guard `calloc(n, *)` with `if (n == 0) return …;` which will address F-02.
- Add `return BUN_MALFORMED;` after the RLE uncompressed-size mismatch detection to handle F-05.
- Update the overlap checks to skip empty sections (addresses F-06).
